# Contact providers — checked 28 September 2026

Recheck official pricing, API access and response schemas in the owner's account before a real pilot. Listed allowances and charges are vendor claims, not measured coverage or accuracy. Never ask for a key in chat; the owner enters their own key directly in Apps Script. No shared account is required.

Apollo's zero-credit search cost does not guarantee access on a Free account. An original owner pilot passed authentication and showed available credits, but both search and email enrichment returned HTTP 403 with a Free-plan access restriction. A second Free account newly registered with a custom-domain work email also authenticated and showed 85/85 lead credits, yet the zero-credit People API Search endpoint returned the same HTTP 403 restriction. Check the exact account and endpoint; a work-email login, successful health request and visible credits do not prove enrichment permissions. The sheet shows search failures explicitly instead of treating them as no matches.

## Implemented Hunter contract

Authentication: `X-API-KEY` header, read from `HUNTER_KEY` Script Property. Fixed HTTPS API origin, redirects disabled; keys never enter query strings. Transport and provider errors expose only a safe status message. No response body or real contact payload is written to Log.

- `GET /v2/domain-search`: domain, `type=personal`, comma-separated `job_titles`, limit=5. Here personal means a named work email, not a private inbox. Reads company domain and `emails[].first_name/last_name/position/linkedin/value/sources/verification`. Local role and domain checks remain necessary.
- `GET /v2/email-finder`: confirmed company domain and full name. Checks returned first/last name and domain before accepting a work email. LinkedIn-only enrichment is deliberately not used as an identity shortcut.
- `GET /v2/email-verifier`: work email only. Retains status; `accept_all`, blocked, disposable or webmail flags override a high score. Records local check time because this endpoint supplies no verification date.

HTTP 202 means pending, 451 means suppression, other non-200 responses stop without automatic retry. Unknown verification stays unknown. Finder/Domain Search can supply dated verification; stale results need a verifier call before publication. A missing profile URL stays blank rather than being generated from a person's name.

The official `test-api-key` serves fixed dummy responses without consuming account credits. It can return a different example person/domain regardless of request inputs; the production identity check must reject that mismatch. `scripts/test_hunter_dummy.py` checks the external schema using fictional inputs only. This is not a real-person accuracy test.

## Choosing a fallback later

Compare additional usable contacts against the incremental credits and plan minimum, on the same target segment. Stop after a fresh verified work email, respect suppression across providers, and record provenance/date per result. Add a second adapter only after its current schema and marginal value are verified; a waterfall is not automatically cheaper. Prospeo's current `/enrich-person` endpoint uses `X-KEY` with `only_verified_email: true`, `enrich_mobile: false` and name/company data; older tutorials can refer to different endpoints.

## Contact order and visible gaps

Reuse existing source contacts and directory phone fields first. In assisted mode, the worker reads explicit emails, phone links (`tel:`), structured organization telephone data, visibly labeled formatted phone numbers and company social links on official pages in bounded batches at zero provider credits, subject to Apps Script fetch quotas. Manual mode leaves this work to the owner. A check completes only when at least one page is readable and no requested page is unavailable or unfinished. Partial checks retry up to three times, at least five minutes apart, then park for owner review; missing contacts remain unknown. Contact receipts are tied to the lead, website and exact company/source identity, expire after thirty days, and preserve owner cell notes. A changed website, company or captured source requires identity confirmation and a new contact check. Do not scrape arbitrary digits, infer a country code, or attribute a public company number to a person. `[Working]` denotes configured internal work. `[Next]` names the remaining owner action or a connected paid tool with its maximum credits. Both labels are treated as missing data. An unreadable site is not proof no contact exists.

Leads separates source handles/links (`contact`), work addresses (`email`) and labeled public/person numbers (`phone`). Source-public emails are not deliverability verified; Contacts keeps the verification and identity states for named people. Paid Apollo phone actions attempt public pages first, then require separate approval for selected people; partial public checks remain explicitly unknown. In assisted mode, submitted phone jobs are polled at zero credits. Approval is followed by another check of the linked lead, current domain and suppression before each selected request. Hunter checks the original person snapshot and exact linked company/source identity again between finder and verifier; changed eligibility retains a found address for review and withholds the second paid request. Pending Apollo phone polls require the same linked active lead, fresh website identity, confirmed current person and suppression eligibility. A malformed search response remains an error; it cannot become a remembered successful empty search. Hover over public contacts for provenance and time checked. Copy valid Apollo phones manually after identity review. Existing company numbers are preserved.

A supplied URL or old lookup note does not establish website identity. All supplied domains require a readable HTTPS homepage and the configured identity check before public scraping, Hunter, Apollo or legacy Google people research. A durable receipt is saved only after a safe row commit, binds the exact company/domain/source evidence, expires after thirty days, and preserves the reviewed Jev or LLM-plus-Jev acceptance method. Homepage redirects are bounded and stay on the requested host, allowing apex/www only; another domain cannot certify the original URL. Supplied-site scores at the existing fallback floor and below the direct threshold require an exact independent choice of that original host. This uses the same acceptance policy as discovered sites; it never lowers a threshold, accepts unreadable evidence or swaps the owner’s URL. Invalid replies and model failures remain retryable, while an explicit rejection requests review. In assisted mode, an unconfirmed URL directs the owner to Fill selected cells. Manual mode directs the owner to review the official company website and contacts.

Guidance describes work that is actually eligible. Sent or otherwise progressed leads point to owner review of the existing conversation. A parked public check asks for review or a selected retry; it cannot advertise Apollo search as running. A pending receipt shows the queued bounded retry only in assisted mode. Delayed guidance writes verify the destination header before committing, and public note refresh removes managed text while retaining owner lines.

Apify is a collection platform, not a universal email/phone directory. Reuse fields already delivered by a tested actor. Enable a new actor only after its source, permission to access, per-run ceiling and useful-contact yield are verified against direct public lookup and optional enrichment. Never start an actor automatically because a contact field is blank.
